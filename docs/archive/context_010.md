# 项目背景

## 场景
在重构、删除功能模块或审查运行时代码变更时需要遵守的完整性检查清单。防止删除不完全导致死代码残留，或变更引入不必要的复杂度。

## 需求

### 代码删除完整性
当删除一个功能或模块时，必须检查以下 8 个区域（遗漏任何一个都会留下死代码或编译错误）：
1. 数据结构、枚举、接口和实现
2. init/reset/destructor 路径
3. 仅为被删行为存在的辅助函数
4. OAM 配置读取和默认值
5. 条件编译块
6. 日志和 trace 点
7. 测试 fixture、helper、测试数据和断言
8. 调用点和接口 override

删除后必须：
- grep 搜索被删除的符号或关键字确认无残留
- 使用 build-sync 进行远程重新编译验证
- 审查最终 diff 排查死引用

### 简洁性审查
合并运行时变更前必须回答以下 6 个问题（任何否定回答都需要先简化再扩展设计）：
1. 每个存储字段是否都有影响行为的真实读取者？
2. 数据结构是否是满足算法需求的最小结构？
3. 状态转换是否从一个明确的位置控制？
4. 一次性操作是否有防重复执行的守卫？
5. 是否优先选择了最简单可行的算法？
6. 配置旋钮是否限制在面向运营商的真实需求范围？

## 关键约束
- 删除操作不做完整检查就会留下编译隐患和死代码
- 简洁性审查是合并前的必要步骤，不是可选的"技术债清理"
